## 0. 总体：四层主栈 + 一条贯穿的服务层

> **来源**：[a16] 第三章「四层架构：一张图看懂主栈」、第四章「两流合一」、
> 第五章「服务层贯穿」；[a5] 第二章「总体架构」。

记住两句话就抓住骨架：**数据流自上而下沉淀，服务流自下而上供给**。

| 层级 | 定位 | 核心内容 |
|---|---|---|
| 应用层 | 业务平台 · 消费与产生 | 9 大平台（数据管理 / 标注 / 训练 / 评测 / 仿真 / 问题分析 / 数据挖掘 / 车云）+ 监控大屏 |
| 接入层 | 多通道统一接入 | Flink CDC 同步 MySQL、Flink 消费 Kafka、OSS 上传承接采集大文件，质量门禁把关 |
| 湖仓底座 | DLF + Paimon · 单一事实源 | ODS / DWD / DWS / ADS 四层加工沉淀，全局 data_id 贯穿 |
| 服务层 | 统一数据服务 · 贯穿全链路 | 元数据 / 数据访问 API / 血缘 / 权限 / 质量监控五大能力，屏蔽 StarRocks 与 Paimon 差异 |

三个设计决策（[a5] 第二章）：**应用层是双角色**（既消费又产生数据，这是闭环能自动转的
关键）、**应用层不碰存储引擎**（全部经服务层 API，换引擎上层无感）、**数据源层与 ODS
一一对应**（任何加工结果都能回溯到原始形态）。

六大设计原则（[a16] 第六章 / [a5] 第二章）：全局数据 ID · 处理版本化 · 闭环视角 ·
分层解耦 · 大文件外置 · 数据资产化。

**本项目落点**：整体骨架体现在包结构本身——`catalog/` 是湖仓底座，`ingest/` 是接入层，
`ads/` 是服务层出口，`controlplane/` + `dataplane/` 是应用层平台的运行态。

## 1. 四层建模：ODS → DWD → DWS → ADS

> **来源**：[a10]《Apache Paimon 分层建模实践》全文；[a5] 第四章。

| 层级 | 职责 | 设计要点 | 本项目表数 |
|---|---|---|---:|
| ODS | 原始同步层 · 原样入湖 | 与数据源一一对应，保留原始信息支持回溯；大文件外置只存路径与元信息 | 33 |
| DWD | 明细数据层 · 清洗关联 | 以 `data_id` 为主轴串联闭环环节，跨源 JOIN 与标准化，血缘与追溯的核心层 | 30 |
| DWS | 汇总指标层 · 聚合分析 | 按业务维度预聚合，**口径在此层固化**，下游不再重复 JOIN | 14 |
| ADS | 应用数据层 · 开箱即用 | 零 JOIN，面向报表 / 大屏 / 应用直接 SELECT | 11 |

「跨源关联后表反而更少，因为消除了冗余」——[a10] 第一章对 ODS → DWD 收缩的解释。

### 1.1 系统字段规范

> **来源**：[a12] 第五章。

| 层级 | 系统字段 | 用途 |
|---|---|---|
| ODS | `_ingest_time` + `_source_system` | 入湖时间 + 来源系统标识，支持多源追溯 |
| DWD / DWS / ADS | `_ingest_time` + `update_time` | 入湖时间 + 业务更新时间，支持增量同步与变更追踪 |

ODS 层用 `_source_system` 换掉 `update_time`——ODS 不做业务更新，记录「数据从哪个系统来」
比「什么时候更新」更有意义。实现见 `domains.py` 的 `Layer.system_fields`。

### 1.2 主键设计三原则

> **来源**：[a12] 第五章。

1. **业务主键优先**——用业务含义明确的字段，不用自增 ID（`data_id`、`training_task_id`）；
2. **复合主键表达完整粒度**——如 `dwd_dataset_version_detail` 的 PK 是 `(dataset_id, version)`；
3. **分区表主键必须含分区字段**——Paimon 硬要求，如 `dwd_mining_image_vector_detail`
   按 `dt` 分区，PK 为 `(image_id, embedding_version, dt)`。

### 1.3 物理策略：分区 / Bucket / changelog-producer

> **来源**：[a12] 第三章（分区决策三规则 + 分区全景表）、第四章（Bucket 五档 +
> changelog-producer 三选一）。

**分区决策三规则**：① 大体量 + 时间范围查询 → 按 `dt` 分区；② 有明确业务分类过滤 →
按业务字段分区；③ 主键 Upsert + 无明确分区维度 → **不分区**（绝大多数 DWD/DWS/ADS 属此类，
通过 bucket 打散，不分区避免小文件过多）。

全湖 **6 张**分区表，照抄原文分区全景表；**Bucket 五档** `{1, 2, 4, 8, 16}`；
**changelog-producer 三选一**口诀：ODS 从 CDC 来 → `input`；DWD 有 Upsert → `lookup`；
DWS/ADS 批量聚合 → `full-compaction`。选错的后果：该用 `lookup` 的表用了 `input`，
下游拿到的 changelog 缺少 `-U` 记录，增量同步数据不一致。

**本项目落点**：`catalog/spec.py` 的 `TableSpec` 把上述全部规则做成**建表期硬校验**——
bucket 必须落在五档、分区字段必须已入主键、changelog-producer 必须与层级匹配。
88 张表 `validate_all()` 零违规，`make validate` 可当 CI 断言跑。

> ⚠️ 原文对 bucket 上限、分区表张数各给了两套互斥说法；88 张表的**字段定义全部是本项目
> 推断**。见 [source-deviations A-4 / A-5 / A-8](./source-deviations.md)。

## 2. 11 数据域与四段式命名

> **来源**：[a12] 第一章（四段式命名公式）、第二章（11 数据域）；[a5] 第四章。

### 2.1 四段式命名公式

```
{层级前缀}_{数据域}_{业务实体}_{粒度后缀}
```

价值是「**表名即文档**」——新人不翻 200 页数仓字典，看表名就知道 80% 的信息。
标准粒度后缀 13 个（原文表格写「10 种」，但三行各含两个后缀）：
`detail` `daily` `statistics` `summary` `relation` `chain` `trace` `dashboard`
`analysis` `info` `config` `log` `event`。

**本项目落点**：`naming.py`。`parse()` 解析四段、`lint()` 产出**非阻断**告警。

> ⚠️ 88 张表里 **27 张不符合原文自己提出的公式**（23 张缺域段、4 张 DWD/DWS 表缺标准后缀），
> 其中包括原文用来演示命名规范的例子。本项目不改表名，逐张登记 + 提供审计命令。

## 3. 三级 ID 体系：闭环可追溯的基石

> **来源**：[a11]《全局 data_id 设计：贯穿智驾全链路的三级 ID 体系》全文；[a5] 第三章。

闭环要可追溯，先得让每条数据有「身份证」。三级 ID 按
「采集单元 → 处理产物 → 处理运行」**逐级派生**：

| 级别 | ID | 锚定对象 | 关键特性 |
|---|---|---|---|
| 一级 | `data_id` | clip 级（约 1 分钟连续采集片段） | 采集端生成，**重刷不变**，终身锚点 |
| 二级 | `artifact_id` | 处理产物（对齐 / SLAM / 标注结果等） | 由「输入 + 算法版本」共同决定，新旧版本并存 |
| 三级 | `run_id` | 产线的一次执行 | 一次执行一条，绑定算法版本与参数快照 |

```
一级 · data_id      COLLECT_BP_20240115143022_a3f8
                      │ 派生（artifact_id 内嵌 data_id）
                      ▼
二级 · artifact_id  COLLECT_BP_20240115143022_a3f8_slam_v3_a1b2c3d4
                      │ 派生（run_id 记录产出该产物的那一次产线执行）
                      ▼
三级 · run_id       run_slam_20240116103000_9f3a21c7
```

**ID 本身即信息**——不查任何表，光看字符串就知道是哪辆车（`BP`）、什么时间采集的、
做了哪个环节（`slam`）、哪个算法版本（`v3`）。

四条核心生成规则（[a11] 第三章）：

1. **唯一性保证**：`data_id` 用 UUID 生成 sequence 部分；`artifact_id` 追加
   `content_hash`——内容相同则 ID 相同，**重试天然幂等**；
2. **时间戳格式**：`yyyyMMddHHmmss`，精确到秒，按时间排序即可还原生产顺序；
3. **重刷处理**：同一 clip 因算法更新重刷产线时，**`data_id` 不变**，新产物生成新
   `artifact_id`，旧产物保留并标记「已被替代」；
4. **关联数据**：衍生产物通过湖仓 `parent_artifact_id` 字段（冗余落表）+ 图数据库关系
   （Neo4j `DERIVED_FROM` 边）关联输入产物，逐级追溯至源头 clip。

第 3 条是整个体系的分水岭：**重刷只改产物、不改锚点**。正因为 `data_id` 终身不变，
「这段数据的所有历史版本」才永远是一句可执行的查询，而不是一个考古问题。

**本项目落点**：`ids/__init__.py`。生成、派生与**反解**（从 ID 字符串还原车辆 / 时间 /
环节 / 算法版本）都在此。`adas-lakehouse id-demo` 可直接演示三级派生与反解。

## 4. 质量门禁：入湖的五步校验链路

> **来源**：[a6]《数据质量门禁设计：智驾数据入湖的五步校验链路》全文；[a5] 第六章末。

「**通道可以分，门禁不能分**」——三条入湖通道共用同一道门禁。

### 4.1 六维检查框架

每一维不仅定义「查什么」，更定义「查出来怎么办」——**处置策略和检查规则同等重要**。

| 维度 | 检查要点 | 处置等级 |
|---|---|---|
| 完整性 | 必填字段非空、记录不缺条、批次不缺片、多模态不缺帧 | 拒绝入湖（硬规则） |
| 准确性 | 数值范围合法、时间戳真实合理、定位无跳变 | 拒绝入湖 / 告警标记 |
| 一致性 | 跨源关联存在性、状态不冲突、元信息与文件本体一致 | 告警标记，允许入湖 |
| 唯一性 | 主键 / 事件 ID 不重复，幂等去重，近重复场景标记 | 自动去重，重复率超限告警 |
| 有效性 | 枚举值在字典内、格式符合规范、状态流转合法、文件可解码 | 拒绝入湖（硬规则）/ 告警 |
| 及时性 | 入湖延迟、CDC 同步延迟、批次到达完整性 | 监控告警（不拦截） |

核心设计是「**严重程度决定处置**」，检查器只输出三种结果：

```
ERROR → REJECT（拒绝入湖）  |  WARNING → ALLOW_WITH_FLAG（带标放行，写 _quality_flag）  |  通过 → ACCEPTED
```

这避免了两个极端：一刀切拒绝会把「时间戳轻微漂移」这类问题全挡在门外，
全部放行又会让脏数据无声无息混进湖仓。

### 4.2 五步异常闭环

门禁的价值一半在「拦」，另一半在「拦下来之后怎么办」：

```
① 门禁拦截 → ② 异常隔离 → ③ 分级告警 → ④ 分流处置 → ⑤ 复验重入湖
```

② 写入隔离表 `ods_quality_issue`，**原始数据不丢失、可重放**；
③ P0 电话 + 钉钉 · P1 钉钉 + 工单 · P2 日报 · P3 周报；
④ A 自动修复（重传 / 幂等重放 / 断点续传）、B 人工修复（源端补数，工单跟踪）、
C 弃置归档（标记原因后归档保留审计）；
⑤ 重新执行全部门禁规则，通过则写入 ODS 并回填处理状态；不通过退回隔离，
**超 3 轮升级 P0**。

四档响应 SLA（避免告警疲劳）：P0 合规级 30 分钟响应 · P1 严重 2 小时响应当日修复 ·
P2 一般 3 个工作日闭环 · P3 观察 连续两周超标升级 P2。

规则不写死在代码里，而是按「检查类型 → 表 → 字段」三级组织成 **YAML 配置**；
规则本身灰度发布，门禁不会成为误杀的瓶颈（[a6] 第三、六章）。

**本项目落点**：`quality/`。`thresholds.py` 是原文全部数字的唯一出处（业务代码里不写
裸数字）、`severity.py` 是分级体系、`rules.py` + `ruleset.py` + `builtin.py` 是规则引擎、
`isolation.py` 是隔离表与重放、`closed_loop.py` 是五步闭环。
YAML 在 `quality/rules/quality_rules.yaml`，Flink 侧在 `flink/sql/quality_gate_pipeline.sql`。

## 5. 血缘双引擎：湖仓管事实，图库管关系

> **来源**：[a13]《Paimon + Neo4j 湖图双引擎数据血缘追溯系统》全文。

一句话：**SQL 数得清行，数不清跳**。多跳遍历用递归 SQL 写会爆炸，用图库是一句 Cypher。
但图库不能持有事实——**Paimon 是唯一事实源，Neo4j 只是关系视图，属性永不双存**。

### 5.1 三级血缘模型

血缘不是一条线，而是三种链交织。每一级由图库的一类关系承载、湖仓的一个冗余字段兜底：

| 血缘类型 | 描述 | 承载方式 |
|---|---|---|
| 实体血缘 | clip → 各环节产物 → 数据集版本的父子链 | 图库 `CONTAINS` / `DERIVED_FROM`；湖仓冗余 `parent_artifact_id` |
| 版本血缘 | 同一环节不同算法版本产物构成版本分支 | 图库 `SUPERSEDED_BY`；湖仓冗余 `superseded_by_artifact_id` |
| 运行血缘 | 每次处理的输入 / 输出 / 参数快照 / 时间 | 图库 `INPUT` / `PRODUCED`；湖仓冗余 `input·output_artifact_ids` |

湖仓侧的事实源是四张 DWD 元信息表：`dwd_collect_clip_detail`（追溯起点，Clip 节点）、
`dwd_production_artifact_detail`（Artifact 节点）、`dwd_production_run_detail`（Run 节点）、
`dwd_dataset_version_detail`（DatasetVersion 节点）。

### 5.2 双链路写入：实时保速度，对账保兜底

双引擎最难的是写一致。答案是「**湖仓唯一事实源 + 图库双链路更新**」——所有血缘事件
先落湖仓，图库两条链路都从湖仓取数：

| 链路 | 机制 | 定位 |
|---|---|---|
| 链路一（事实源） | run / 产物 / 数据集版本写入湖仓四张表，关系字段冗余落表 | 一切血缘的出发点 |
| 链路二（实时） | 监听湖仓 binlog / 变更消息，`MERGE` 图库节点与关系 | 低延迟；**失败不阻塞湖仓写入** |
| 链路三（对账） | T+1 扫描湖仓增量（`_ingest_time`），按关系字段 UPSERT 补齐 | 兜底；**幂等可重复执行** |

`MERGE` 幂等是一切的前提。

### 5.3 查询协同：图库找关系、湖仓取明细

一次完整的血缘查询按三步走：

```
① Neo4j 多跳遍历找路径、定范围（只返回节点 ID 与关系类型）
② 按节点 ID 回 Paimon 补齐属性、参数快照与质量指标
③ 组装输出带数据来源的血缘结果
```

四个查询方向覆盖闭环全部追溯场景：**正向追踪**（这批采集数据最终用在哪些数据集与模型上）、
**反向追溯**（这个 Badcase 是哪个版本模型、什么参数跑出来的）、**版本分支对比**
（同一批数据，SLAM v3 与 v4 哪个质量更好）、**影响分析**（算法升级后，哪些数据集与
训练任务需要重刷）。

**本项目落点**：`lineage/`。`model.py` 是三级血缘模型、`graph.py` 是 Cypher 建图与查询、
`sync.py` 是双链路写入、`resolver.py` 是「图库定范围 → 湖仓补明细」的两段式解析、
`query.py` 是四个查询方向。Flink 侧在 `flink/sql/lineage_realtime_sync.sql`（链路二）
与 `lineage_reconcile_t1.sql`（链路三）。

## 6. 双路查询与语义检索

> **来源**：[a5] 第七章「数据用得上：双路查询与语义检索」（系列二第 3 篇《双路查询架构》
> 本身不在本仓库的 16 篇快照内，双路查询部分以 [a5] 为准）；
> 向量部分来源 [a7]《HNSW 向量索引落地 StarRocks》全文；VARIANT 部分来源 [a9]。

### 6.1 StarRocks + Paimon 双路

| 路径 | 机制 | 适用 |
|---|---|---|
| 外部表即席查 | StarRocks 经 External Catalog 直查 Paimon | 零冗余零搬运，Paimon 保持单一事实源；探索式分析与临时取数 |
| ADS 内表物化 | 高频应用指标物化为 StarRocks 内表 | 毫秒级响应、稳定可控，不受湖端 Compaction 影响；监控大屏与固定报表 |

选路按负载对号入座：高频毫秒级 → 内表；灵活秒级可接受 → 外部表直查；
语义检索 / 相似样本圈选 → 向量索引 + 标量过滤。

### 6.2 向量检索：不新增一套数据库

**向量落湖于 Paimon，HNSW 索引建在 StarRocks 外部表上**——向量数据只有一份，
事实源依然唯一。索引参数照抄原文 **[a5] 第七章**：**cosine 距离、M=16、efConstruction=200**，
**按分区增量刷新**（每日增量只重建当日分区索引，千万级全量索引不用每天重刷）。

> ⚠️ 出处说明：`M=16` / `efConstruction=200` 只在 [a5] 第七章正文出现；子系统主文 [a7]
> 第四章的索引 DDL 是图片，第六章只写「M / efConstruction 在 POC 阶段按数据规模压测定参」。
> 两篇不矛盾（方法 vs 压测结论），但这两个数必须标 [a5]。检索期的 `efSearch` 原文两篇
> 都没给，本项目默认 128，见 [source-deviations B-6](./source-deviations.md)。

**双索引**对应图文双向量：文搜图走文本向量、图搜图走图片向量、混合检索两个都用。

外部表向量索引是相对新的能力，原文明确要求全量上线前先过 **POC 五项前置验证**：
多向量列同表索引支持度 / 分区级索引支持度 / 索引构建耗时 / 增量刷新延迟 /
**千万级检索 P95 ≤ 2 秒（整条链路的验收线）**。

降级路径在设计之初就留好：若 POC 验证外部表索引性能不达标，
**向量数据冗余写入 StarRocks 内表**兜底。

半结构化元数据列 `vector_meta` 用 **Paimon 2.0 VARIANT** 落地（依据 [a9]）——
避免「存 JSON 字符串写入轻松但每次查询重新解析」与「拆 STRUCT 读取高效但上游改字段
全链路跟着演进」的两难。

**本项目落点**：`vector/`。`params.py` 是索引参数与刷新调度、`index.py` 是 HNSW 建索引、
`embedding.py` 是五步 Embedding 流水线、`search.py` 是统一检索 API 与四类检索能力、
`backend.py` 是外部表 / 内表双后端与降级、`variant.py` 是 VARIANT 落地。
双路查询路由在 `ads/routing.py` 与 `dataplane/query.py`，物化在 `ads/materialize.py`。

## 7. 存储生命周期：五级分层成本治理

> **来源**：[a14]《存储生命周期五级分层：智驾 PB 级数据成本治理实战》全文；[a5] 第八章③。

数据闭环是一个「**只进不出**」的增长系统——采集、量产回传、产线中间副本、训练
Checkpoint、数据集版本、仿真突发数据六大增长源叠加，存储按月近线性增长。
不治理的三重代价：高价介质滥用（**NAS/CPFS 单价约为 OSS 标准存储的 8~10 倍**）、
冷数据占据热层、成本指数级增长。

### 7.1 三类介质与五级分层

数据在三类介质间流转：
**OSS 为唯一事实源 → 训练前预热上 NAS → 训练后淘汰回 OSS → 按温度逐级降冷**。

| 分层 | 存储介质 | 进入条件 |
|---|---|---|
| 热 H1 | CPFS / NAS | 数据集关联活跃训练任务并预热；训练结束 **7 天缓冲**后淘汰 |
| 温 H2 | OSS 标准存储 | 创建 **30 天**内，或 30 天内有访问 |
| 冷 C1 | OSS 低频存储 | 连续 **90 天**无访问 |
| 归档 C2 | OSS 归档 / 深度归档 | 连续 **180 天**无访问且过保留策略阈值，取回 ≤4 小时 |
| 删除 D | —（无介质） | 过保留期 + **血缘零引用** + 白名单校验，**三重确认同时满足** |

**介质相对单价**（[a14] 第二章第二张表，基准 = OSS 标准存储；原文注明「示意值，
以云厂商实际计价为准」）——这是另一个维度，五级分层说的是「数据处于哪一档生命周期」，
下表说的是「这档数据落在哪种介质、这种介质多贵」：

| 存储介质 | 单价量级（相对） |
|---|---|
| CPFS / NAS | 约 **8–10x** |
| OSS 标准存储 | **1x（基准）** |
| OSS 低频存储 | 约 **0.5x** |
| OSS 归档 | 约 **0.15x** |
| OSS 深度归档 | 约 **0.05x** |

同一份数据放在归档层的价格只有热层的 **1/50 甚至更低**。

> ⚠️ 三个维度不要混：**五级分层**（生命周期档位，5 档，删除档无介质）、
> **storage_media**（介质枚举，5 值：`nas` / `oss_standard` / `oss_ia` / `oss_archive` /
> `oss_deep_archive`）、**lifecycle_stage**（落表字段取值域，6 值：`hot` / `warm` /
> `cold` / `archive` / `pending_delete` / `deleted`——删除档在字段上拆成待删与已删两态）。
> 代码里分别对应 `tiers.TIERS` / `tiers.StorageMedia` / `tiers.LifecycleStage`。

### 7.2 元信息驱动 + 日级调度闭环

治理决策全部由两张湖仓表驱动（[a14] 第四章），调度按
「**扫描决策 → 演练审计 → 执行 → 回写 → 告警**」日级闭环运行，
每次预热量 / 淘汰量 / 降冷量 / 成本变化全部回写湖仓，**成本环比增长超 10% 自动告警**。

一笔真实的成本账（[a14] 第六章 / [a5] 第八章）：一份 **240GB** 的雨夜城区采集数据，
常年驻留 NAS + OSS 标准，年成本约 **¥3,226**；走治理流程（预热上 NAS 仅占 9 天 →
训练后淘汰回温层 → 30 天无访问降冷 → 90 天无访问归档），年成本压到 **¥203**，
**降幅约 94%**。

更关键的是最后一步：这份数据过 365 天保留期时，因仍被数据集版本引用（血缘引用数 > 0），
被删除三重确认拦截、继续留存——**降冷可以激进，删除必须保守，训练永远可复现**。

**本项目落点**：`lifecycle/`。`tiers.py` 是五级分层与阈值、`policy.py` 是保留策略、
`cost.py` 是成本模型与那笔 240GB 的账、`decision.py` 是扫描决策、
`scheduler.py` 是日级调度闭环与四道安全闸、`records.py` / `tables.py` 是两张元信息表。
Flink 侧在 `flink/sql/lifecycle_state_sync.sql` 与 `lifecycle_writeback.sql`。

## 8. 挖掘平台：控制面 / 数据面分离

> **来源**：[a4]《数据挖掘平台架构设计：控制面/数据面分离的工程实践》全文；
> 平台的三个引擎另见 [a3]（分层抽帧）、[a1]（规则挖掘）、[a2]（统一标签体系）。

### 8.1 第一设计原则：平台不持有主数据

原文第二章给的反面教训：很多团队做挖掘平台踩的最大的坑，是平台顺手建了一套自己的
「数据副本」——抽帧结果存一份、标签存一份、向量再存一份，时间一长口径就分裂了。

判断一个平台设计是否健康的简单标准（[a4] 第四章）：

> **把平台的数据库清空重建，业务数据是否完好？** 如果是，控制面 / 数据面才算真正分离。

### 8.2 五层应用架构

| 层级 | 核心组件 | 设计要点 |
|---|---|---|
| 接入层 | Web 控制台 + OpenAPI 网关 | 统一入口，认证 / 限流 / 审计，**OpenAPI 为唯一对外通道** |
| 应用服务层 | 统一检索 / 任务管理 / 统一标签 / 圈选导出 / 审核流，五个微服务 | 全部无状态可水平扩展，随检索 QPS 用 HPA 扩缩 |
| 核心引擎层 | 抽帧（K8s Job）/ 规则挖掘（Spark 批 + Flink 流）/ VLM 推理（Ray + GPU）/ Embedding 流水线 | 计算密集，各引擎独立调度独立扩容，互不阻塞 |
| 平台支撑层 | MySQL / Redis / Kafka / OSS / 模型注册表 | **只存平台自身运行态，主数据一律不进** |
| 外部依赖 | DLF + Paimon / StarRocks / DolphinScheduler / GPU 资源池 | 数据面全部外部化，平台无状态可随时重建 |

关键是「引擎与服务解耦、**引擎之间也解耦**」：抽帧结果写入
`dwd_mining_image_frame_detail` 之后，规则挖掘与 VLM 推理各自基于该表独立运行，谁也不等谁。

### 8.3 两面的边界

| 面 | 内容 |
|---|---|
| **控制面**（平台本地） | MySQL 存规则配置、任务配置与执行状态、审核流状态；Redis 存检索热点与字典热缓存——全部是「平台自身运行态」，体量小、可随时重建 |
| **数据面**（湖仓） | clip / 图片 / 标签 / 向量全部在 Paimon，StarRocks 只做查询与向量索引加速，同样不持有主数据 |
| **控制面回流数据面** | 规则配置经 Flink CDC 同步入湖（`ods_mining_rule_config`），任务与审核动作定期回写 `dwd_mining_task_detail`——**平台的每一步操作都进血缘** |

部署按「**K8s 三区 + 托管依赖**」组织：在线服务区（无状态 + HPA）、
计算引擎区（批处理窗口期弹性扩容，跑完即释放）、GPU 区（分时复用）。

### 8.4 平台的三个引擎

- **分层抽帧**（[a3]）——**三道成本闸门**：常规抽帧（普查，默认 2 秒 1 帧，保留 1/60）→
  事件抽帧（现场勘查，事件前 15 秒 + 后 5 秒共 20 秒窗口，1 秒 1 帧）→
  推理抽帧（**用打分代替随机选帧**）。落点 `sampling/`。
- **规则挖掘**（[a1]）——**规则即数据**，配置也是湖仓资产；六大规则种类
  （标签组合 / 时空地理 / 车辆信号 / 模型输出 / 事件触发 / 多条件复合）；
  **批流双模**，执行模式跟着条件来源走，不是一刀切。落点 `mining/`。
- **统一标签体系**（[a2]）——一套统一标签字典（五大类别受控词表）+ 一条三源收口管道
  （字典映射 → 幂等去重 → 血缘填充）+ 一套**四态生命周期**治理，**防标签爆炸**；
  与质量门禁联动：**未审核标签进不了训练集**。落点 `tags/`。

### 8.5 挖掘的双出口

[a4] 第一章 / [a5] 第一章：数据挖掘是闭环的「**变速箱**」——
**库内命中场景直接回补训练集（零采集成本），未命中才下发定向采集需求**，
把闭环成本压到最低。

**本项目落点**：`controlplane/`（控制面：任务编排 / 规则下发 / 状态管理 / OpenAPI）
与 `dataplane/`（数据面：引擎接入 / 执行 / GPU 分时 / 查询）。
两面的边界契约定义在 `controlplane/contracts.py`。

## 10. 三通道入湖与合规链路

> **来源**：[a5] 第六章；[a8]《采集数据的合规入湖链路》全文。

| 通道 | 承接数据 | 机制 |
|---|---|---|
| Flink CDC | 各平台 MySQL 业务库 | 读 binlog 实时同步，「全量快照 → 增量 binlog → 断点续传」三阶段，**业务库零侵入不改代码** |
| Kafka | 事件流（产线埋点 / 训练指标 / 车端触发） | Flink 实时消费落表，**保留事件回放能力**，消费失败可从上次位点重消费 |
| OSS 合规上传 | 采集大文件（图像 / 点云 / 传感器数据） | **五步合规链路**：车端脱敏 → 合规室上传 → 合规云脱密 → 智驾云分发 → 实时入湖 |

**双脱敏机制**（[a8] 第三章）：车端简单脱敏保证离车即合规，合规云复杂脱敏补齐车端做不了
的部分（删除敏感 POI、模糊桥梁限高数值）；合规云与智驾云同 VPC 内网流转、不对外暴露——
**合规靠架构边界，不靠流程承诺**。

**大文件外置**贯穿三通道：图像、点云这类几十 GB 的文件**从不进湖**——本体存 OSS，
湖仓只存路径与元信息（文件大小、脱敏标记、校验和、归属 `data_id`）。

三条通道共同终点：统一经质量门禁校验后写入 ODS 层（见第 4 节）。

**本项目落点**：`ingest/`。`channels.py` 是三通道、`compliance.py` 是双脱敏与合规标记、
`oss.py` 是 OSS 大文件外置、`gate.py` 是与质量门禁的衔接、`pipeline.py` 是五步合规链路。
Flink 侧在 `flink/sql/ingest_cdc_mysql.sql` / `ingest_kafka_event.sql` /
`ingest_oss_file_meta.sql`。
